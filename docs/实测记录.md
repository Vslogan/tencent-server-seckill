## 返回码对照

| code | msg | 含义 |
| --- | --- | --- |
| `0` | ok | 下单成功，`data.deal_names` 即订单号 |
| `408` | 系统访问频率过快，请稍后再试 | 风控限流。整点并发下最常见，属预期噪声 |
| `1100110` | 正在执行其他操作，请稍候再试 | 同账号已有下单在途，并发互斥 |
| `1100106` | 相同实名认证主体已购买此产品 | 首单资格已用掉，需换主体 |
| `1100202` | 账号需要进行人脸核身校验 | 需先去 `act/pro/face_authentication` 完成校验 |
| `1100205` | 当前系统繁忙，请稍后重试 | 服务端过载 |
| `1101001` | 抱歉，秒杀尚未开始 | 预热请求的正常结果 |

## 观察

- **10-09 全部被 `408` 挡住**：三场共 450 次请求全是 `系统访问频率过快`，一次 `code=0` 都没有。
  同一天没有任何成功，说明当天的失败不是并发不够，而是账号被限流。
- **10-10 15:00 场次出现了 `1100202`（人脸核身）和 `1100205`（系统繁忙）**：限流之外的新拦截。
  人脸核身没提前做完的话，抢到了也下不了单——建议开抢前先在活动页完成核身。
- **成功时请求数只有 10**：都是第一批并发就命中，不需要打满 10 秒。
  并发里同时出现 `1100110`（其他操作在途）属正常，说明是同一批请求在抢同一把锁，
  只要有一条拿到 `code=0` 就算成功，脚本随即 break。
- **`408` 与成功可以共存**：10-11 两场里，10 条请求中 5–6 条是 `408`，1 条 `code=0`。
  所以看到 `408` 不等于没抢到，要看有没有 `code=0`。
